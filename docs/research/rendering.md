# Rendering and GStreamer research

Date: 2026-11-21
Scope: replace UxPlay's `renderers/` code in a standalone Rust application while retaining its current GStreamer pipeline behavior on Linux, macOS, BSD/Unix, and Windows.

## Source behavior to preserve

- `renderers/CMakeLists.txt:41-44` links GLib plus GStreamer core, SDP, video, and app libraries. The legacy C build declares GStreamer 1.4 as its baseline; it also has conditional paths for newer versions.
- `renderers/audio_renderer.c:74-105` checks that the `app`, `libav`, `playback`, `autodetect`, and `videoparsersbad` plugins/features are installed. It builds one live `appsrc` pipeline per audio renderer, supplies ALAC or PCM caps, pushes timestamped buffers, and drains/changes pipeline state on stream resets and errors (`:148-239`, `:247-305`, `:371-444`). Audio RTP mode converts to 44.1 kHz stereo S16BE and uses `rtpL16pay` (`:193-198`).
- `renderers/video_renderer.c:329-359` uses GStreamer `playbin` or `playbin3` for HLS; for mirrored video it creates a live `appsrc` pipeline from the selected parser, decoder, converter, sink, and optional user pipeline (`:376-482`). Buffers, end-of-stream, state changes, HLS seek/buffering, and bus errors are part of the observable behavior (`:622`, `:663`, `:823-1035`). The sink defaults are `autovideosink` and `autoaudiosink`; the CLI also permits platform-specific sink names and options (`uxplay.cpp:113`, `:118`, `:1141-1169`).
- `renderers/mux_renderer.c:120-160` creates a live audio/video `appsrc` pipeline ending in `mp4mux` and `filesink`; it sets H.264/H.265/ALAC caps and uses fragmented MP4. Preserve packet timestamps, stream combinations, path escaping, file rotation, and EOS/finalization (`:171-215`, `:231-301`).
- X11/window integration is not entirely in the renderer crate: `renderers/video_renderer.c:34-35`, `:455-482` sets a native window handle through `GstVideoOverlay`; `renderers/x_display_fix.h` contains extra X11-specific behavior. The CMake file can omit X11 dependencies, so retain that optional build/runtime path.

## Rust bindings and fit

| Need | Rust interface | Fit | Conditions |
|---|---|---|---|
| Core elements, caps, buffers, state, bus, pipeline creation | `gstreamer` | Good | Safe bindings cover the native GStreamer API. Use `gstreamer::parse::launch` / `launch_full` for the same pipeline-description parser used by `gst_parse_launch`; do not write a second parser for user pipelines. |
| Feed decoded/network buffers into live pipelines | `gstreamer-app` (`AppSrc`) | Good | Bindings expose appsrc, caps, push-buffer, and end-of-stream. Preserve the current buffer metadata and timing. |
| Video overlay, orientation/navigation and video helpers | `gstreamer-video` | Partial | The overlay interface is bound, but attaching an external native window handle is an unsafe Rust method and must be isolated with a `// SAFETY:` justification; X11-specific fixes remain platform code. |
| GLib main loop / main context | `glib` | Good | Use one owned main context for bus watches and UxPlay callbacks, and keep teardown of sources/watches explicit. |
| HLS and playback | `gstreamer` core `playbin`/`playbin3` elements | Good, plugin-dependent | The current source directly creates playbin elements; it does not need the separate `gstreamer-player` crate. Preserve the selected playbin generation, flags, URI, buffering, seek, and bus handling. |
| Video/audio decode, output sinks and MP4 mux | Installed GStreamer plugins | Partial as a Rust dependency | Rust crates do not supply the codec, sink, or muxer plugins. Use the installed native plugins and verify factories at startup just as the C implementation does. |
| All-in-one self-contained renderer with no native media runtime | No fitting Rust binding | None | `gstreamer-rs` is a binding layer over native GStreamer. The pure-Rust application can remove its own C source while still requiring native GStreamer libraries, plugins, codecs, and OS sink support at runtime. |

Current stable crate versions observed on docs.rs: `gstreamer 0.25.4`, `gstreamer-app 0.25.2`, `gstreamer-video 0.25.4`, and `glib 0.22.11`. Keep the GStreamer Rust crates in the 0.25 family and lock the actual resolved versions in `Cargo.lock`; their release numbers are not identical across every sub-crate. The core crate's optional version features are cumulative (`v1_16` through `v1_30`) and default features add no GStreamer version APIs. Enable only what source behavior needs; the Rust macOS main wrapper is available behind `v1_22`.

Primary references: [gstreamer](https://docs.rs/gstreamer/latest/gstreamer/), [gstreamer-app](https://docs.rs/gstreamer-app/latest/gstreamer_app/), [gstreamer-video](https://docs.rs/gstreamer-video/latest/gstreamer_video/), [glib](https://docs.rs/glib/latest/glib/), [gstreamer-rs installation and platform notes](https://github.com/GStreamer/gstreamer-rs), and [the Rust macOS wrapper](https://docs.rs/crate/gstreamer/latest/source/src/macos.rs).

## Cross-platform runtime/build constraints

- The current Rust bindings require GStreamer and `gst-plugins-base` at least 1.14. UxPlay's CMake asks for GStreamer 1.4, so adopting current bindings raises the declared minimum. Make that change explicit in the plan/packaging; if 1.4 remains a hard compatibility requirement, investigate an older binding set or a tiny version-gated FFI layer before implementation. `playbin3`, modern sinks, and some current app features also depend on newer installed plugins.
- Linux and BSD builds need GStreamer and development headers from the target system/package manager. Plugin modules are separately installed and vary by distribution. The upstream bindings list base/good/bad/ugly/libav plugin packages as sources of optional features; only the exact factories used by UxPlay should be marked required.
- macOS needs the runtime and development framework/bundles. Upstream documents universal framework installers; keep GStreamer `pkg-config` first on the build path. For framework builds, preserve the current `gst_macos_main` initialization path: `gstreamer::macos_main` is available behind the `v1_22` feature.
- Windows packages must match the Rust ABI (MSVC vs MinGW). The upstream Rust binding installation guide recommends official GStreamer binaries and requires the matching runtime/development installers; keep its `pkg-config` ahead of other copies. This workspace's Rust host uses MinGW, matching UxPlay's documented MSYS2/MinGW build, so use the matching MinGW GStreamer packages for Windows development.
- Do not assume `cargo build` proves rendering works. The deployed program also needs the right GStreamer shared libraries, plugin registry/scanner, codecs, `playbin` elements, `mp4mux`, and sink plugin for the selected OS/session. An installed factory may still be unusable if a hardware decoder, display server, audio server, or plugin-specific native library is absent.

Primary references: [gstreamer-rs installation requirements for Linux/BSD/macOS/Windows](https://docs.rs/gstreamer-app/latest/gstreamer_app/), [GStreamer binary downloads](https://gstreamer.freedesktop.org/download/), and [GStreamer plugin modules](https://gstreamer.freedesktop.org/modules/index.html).

## Semantic traps and proof points

1. **`appsrc` ownership, queueing, and time.** `push_buffer` queues into an internal streaming thread and retains its own buffer reference; a full queue can signal `enough-data` or block when configured. Match source caps (`audio/x-alac`, S16LE PCM, H.264/H.265 AU alignment), `is-live`, `format=time`, PTS/DTS/duration, base-time handling, and EOS order. Cover stream reset/reconnect, discontinuity, empty/malformed frame, and blocked/downstream-error cases. [GStreamer appsrc reference](https://gstreamer.freedesktop.org/documentation/app/appsrc.html), [Rust AppSrc reference](https://docs.rs/gstreamer-app/latest/gstreamer_app/struct.AppSrc.html).
2. **State changes are asynchronous.** Pipeline state changes and playbin errors complete on background threads; observe the bus and preserve the current order of READY/PLAYING/NULL transitions and EOS before teardown. Do not assume that a successful `set_state` means decoding/rendering has started. [GStreamer playbin reference](https://gstreamer.freedesktop.org/documentation/playback/playbin.html), [GStreamer bus reference](https://gstreamer.freedesktop.org/documentation/application-development/basics/bus.html).
3. **Window-handle callback thread.** `prepare-window-handle` may be raised from a streaming thread and needs a synchronous bus handler; GUI/window-system calls from that thread are not generally safe. Keep the callback tiny, pass only the pre-created platform handle, and encapsulate the unsafe `set_window_handle` call with a safety comment. Preserve the `autovideosink` path where the sink owns its own window. [GstVideoOverlay reference](https://gstreamer.freedesktop.org/documentation/video/gstvideooverlay.html), [Rust VideoOverlay API](https://docs.rs/gstreamer-video/latest/gstreamer_video/struct.VideoOverlay.html).
4. **User pipeline strings are API.** Options such as `-vs`, `-as`, `-vrtp`, and `-artp` feed GStreamer element/pipeline descriptions. Keep the original parser and error path (`parse::launch*` returns the native parse error); do not tokenize or sanitize the string into a different pipeline grammar. [Rust launch API](https://docs.rs/gstreamer/latest/gstreamer/parse/fn.launch.html).
5. **Plugin presence is runtime state.** Reproduce factory checks and missing-plugin diagnostics. Test H.264, optional H.265, ALAC audio, HLS on playbin2 and playbin3, each mux mode, each sink override, and unavailable-plugin errors separately. The pipeline is the behavior contract; crate compilation alone cannot prove it.
6. **MP4 finalization and timestamps.** The mux pipeline is fragmented, receives encoded source buffers rather than decoded frames, and must receive EOS before close. Verify exact output file sequence/names, audio-only/video-only/mixed streams, fragmentation duration, and playable output after stop/reset.

## Recommendation

Keep GStreamer as the native media engine and port the UxPlay-owned orchestration to Rust with `gstreamer`, `gstreamer-app`, `gstreamer-video`, and `glib`. Reuse `parse::launch` so current custom pipelines and sink options continue to work. Keep plugin installation external and document platform packages separately. Build one renderer module with per-client pipelines and one GLib main-context integration; make X11/native-window handling a narrow platform adapter. Before coding, record an ADR for the GStreamer 1.14 minimum (vs the source's 1.4 CMake floor) and the native-runtime packaging requirement.
