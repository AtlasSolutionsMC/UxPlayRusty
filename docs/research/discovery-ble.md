# Discovery and BLE port research

**Scope.** This report covers the original UxPlay mDNS/DNS-SD and BLE-beacon implementations and Rust integration candidates. Local behavior references point to the supplied source tree at `D:\Save\Uxplay\UxPlay`. External references are upstream project documentation, Microsoft/Apple/BlueZ documentation, or docs.rs. Version observations are current as of 2026-11-21.

## Findings and recommendation

- Use a **small discovery adapter** with two explicit modes: an embedded responder based on `mdns-sd`, and an OS DNS-SD registration backend based on `dns-sd-native` (or an equivalent native adapter). Keep the original `USE_MDNS` / `USE_DNS_SD` selection observable in the Rust CLI/config. `mdns-sd` covers an embedded Rust responder on macOS, Linux, and Windows, but its documented OS list does not establish BSD support. The original built-in responder is in-tree and used on BSD too, so BSD must be a build-and-network acceptance gate; if `mdns-sd` cannot support the target BSDs, port the narrow `lib/mdnsd` functionality or make the Avahi/native dependency explicit. [mdns-sd support and architecture](https://docs.rs/crate/mdns-sd/0.21.7), [dns-sd-native platform table](https://docs.rs/crate/dns-sd-native/0.1.1)
- Model BLE as a **portable payload builder plus OS/hardware backends**: BlueZ over D-Bus on Linux, WinRT through Windows APIs on Windows, serial AT control for BleuIO, and a separately selected privileged HCI backend for Linux/*BSD. There is no common Rust API that removes the platform/hardware contracts. `bluer` is a strong fit for the BlueZ path; `windows`/WinRT bindings and `serialport` fit Windows and serial paths. [bluer Advertisement](https://docs.rs/bluer/latest/bluer/adv/struct.Advertisement.html), [windows-rs](https://github.com/microsoft/windows-rs), [serialport](https://docs.rs/serialport/latest/serialport/)
- Use the `plist` crate’s typed values and binary parser/writer for Apple binary plists. Preserve plist semantics first, then prove any byte-level equivalence with fixtures; equivalent dictionaries can serialize in a different key order. [plist API](https://docs.rs/plist/latest/plist/)

## Source behavior to preserve

The build selects the OS DNS-SD path when `USE_DNS_SD` is set or on Apple unless `USE_MDNS` is set; otherwise it uses the internal `lib/mdnsd/dnssd_mdnsd.c` adapter. The external adapter registers both `_raop._tcp` and `_airplay._tcp`, and constructs TXT records. References: `D:\Save\Uxplay\UxPlay\CMakeLists.txt:60-78`, `lib\dns_sd\dns_sd.c:234-379`, and `lib\mdnsd\dnssd_mdnsd.c:70-150`.

BLE backend selection defaults to WinRT on Windows, BlueZ on Linux, and BleuIO elsewhere; HCI is explicitly selectable for Linux/*BSD. The Python dispatcher is dynamic-import based (`Bluetooth_LE_beacon\uxplay-beacon.py:425-433,487-502`), so port it into an explicit Rust enum and backend factory rather than preserving import-by-string behavior. The source exposes BLE interval, adapter index, serial device, IP, and backend selection options; WinRT ignores interval settings while BlueZ/BleuIO use min/max intervals (`uxplay-beacon.py:288-310,442-468`).

All payload paths encode Apple manufacturer ID `0x004C` and a manufacturer body consisting of `09 08 13 30`, the four IPv4 bytes, and the port as two big-endian bytes. BlueZ and WinRT provide company ID separately; HCI/BleuIO compose the full manufacturer AD field themselves. References: `uxplay_beacon_module_BlueZ.py:108-122`, `uxplay_beacon_module_winrt.py:55-74`, `uxplay_beacon_module_BleuIO.py:68-92`, and `uxplay_beacon_module_HCI.py`. Keep one tested Rust encoder that returns the body and AD structure separately to avoid double-prefixing the company ID.

## mDNS, DNS-SD, and Bonjour

### Embedded Rust responder

`mdns-sd 0.22.0` provides service registration, browsing and address resolution with a background daemon thread and channel API, without requiring an async runtime. `ServiceInfo` constructs PTR/SRV/TXT and A/AAAA records; `ServiceDaemon` registers and gracefully unregisters service instances. It has IPv4/IPv6 handling, and lets the application set interfaces and whether conflict probing is required. This is a reasonable default replacement for the in-tree responder on its documented macOS/Linux/Windows targets. [crate overview](https://docs.rs/mdns-sd/0.22.0/mdns_sd/), [ServiceInfo](https://docs.rs/mdns-sd/latest/mdns_sd/struct.ServiceInfo.html), [ServiceDaemon](https://docs.rs/mdns-sd/latest/mdns_sd/struct.ServiceDaemon.html).

This is safe Rust for the protocol/responder layer, but still relies on OS multicast sockets, available interfaces, and multicast joins. A port bind/join failure remains an environment or OS issue. `mdns-sd` 0.22.0 returns an error if both IPv4 and IPv6 sockets fail to bind; with just one socket unavailable, it can still run. Apple P2P interfaces `awdl0` and `llw0` are excluded by default and can be included with `include_apple_p2p(true)`; verify the old UxPlay behavior on Apple Wi-Fi/AWDL before enabling that option. [ServiceDaemon API](https://docs.rs/mdns-sd/latest/mdns_sd/struct.ServiceDaemon.html).

**Compatibility checks:** UxPlay registers both RAOP and AirPlay names and has a custom TXT list. Keep the exact instance-name escaping, hostname, address selection, ports and TXT values. `mdns-sd` defaults to probing name conflicts; native Bonjour/Avahi behavior and the old internal responder may rename/report conflicts differently. It truncates an overlong TXT property string to its supported 255-byte limit, so validate input before constructing one. [ServiceInfo constraints](https://docs.rs/mdns-sd/latest/mdns_sd/struct.ServiceInfo.html).

### OS DNS-SD mode

The original native mode uses DNS-SD API calls: on Windows it dynamically loads `dnssd.dll`, on Unix-like systems it dynamically loads `libdns_sd.so` (or links the Apple API), then registers RAOP and AirPlay and reports registration errors. See `lib\dns_sd\dns_sd.c:130-211,234-379,480-500`. This is a **native service/API mode**, not an embedded pure-Rust mDNS implementation.

`dns-sd-native 0.1.1` is a Rust/Tokio registration wrapper for macOS’s DNS-SD framework (macOS 10.12+), Windows’ native Win32 DNS-SD API (Windows 10+), and Avahi over D-Bus on Linux/FreeBSD. It registers services only. On Linux/FreeBSD the Avahi daemon must already be running; the wrapper avoids a libavahi link dependency but registration still fails without that system service. Thus it fits the external-registration mode with explicit prerequisites, but does not replace embedded default behavior or the broad browsing API. [crate platform/API description](https://docs.rs/dns-sd-native/latest/dns_sd_native/), [crate README](https://github.com/bzld/dns-sd-native). A separate `mdns-sd-discovery` crate covers native browsing through macOS, Windows, and Avahi backends, if UxPlay ever needs browsing via DNS-SD rather than only advertising. [mdns-sd-discovery](https://docs.rs/mdns-sd-discovery/latest/mdns_sd_discovery/).

**Recommended interface:** define `DiscoveryBackend::{Embedded, NativeDnsSd}` behind `register_raop`, `register_airplay`, `unregister`, and `shutdown`. Build TXT records once in shared code. Map each backend’s conflict/error callbacks into UxPlay-compatible messages and process lifetime. Do not silently auto-fallback between modes: the original switch is intentional and a fallback can change which daemon owns announcements or which prerequisites are required. Verify interface/address selection and service-name conflict behavior against packet captures.

**Version-sensitive:** docs.rs currently publishes `mdns-sd 0.22.0` (2026-11-15). Its changelog records breaking API and behavior changes: `status()`’s running variant now carries a `RunningState`; constructor failures are returned where prior versions could report running despite both sockets failing; and escaped service fullnames preserve their escapes. Pin a reviewed version and test these behaviors instead of coding to `latest`. [0.22.0 changelog](https://docs.rs/crate/mdns-sd/0.22.0/source/CHANGELOG.md).

## Property lists

UxPlay parses binary plists from AirPlay control messages and emits binary plist responses throughout `lib\raop_handlers.h`, `lib\http_handlers.h`, `lib\raop.c`, and `lib\raop_rtp_mirror.c`. The code uses dictionaries, arrays, strings, data blobs, booleans, integers, and reals. A Rust port can use `plist::Value`, `plist::from_bytes` / `from_reader`, and `to_writer_binary`; the crate exposes integer values that can hold `i64` or `u64`, data, date, and UID variants. This protocol serialization can be Rust-only and does not require Apple frameworks. [plist 1.10.4 API](https://docs.rs/plist/latest/plist/).

For replay compatibility, compare parsed plist trees and HTTP framing first, then compare serialized output when AirPlay peers care about byte-level details. Dictionary ordering and integer-width choices can vary without changing the plist value; do not assume byte-identical output just because both writers emit binary plist. Arrays, booleans, data lengths, reals, optional/missing keys, and large unsigned values must retain their types and values. `plist::Dictionary::sort_keys` exists but is documented as useful for deterministic XML; it is not evidence that it reproduces libplist’s binary ordering. [Dictionary API](https://docs.rs/plist/latest/plist/dictionary/struct.Dictionary.html).

## BLE backends and constraints

| Original mode | Rust fit | System/hardware requirement | Port notes |
|---|---|---|---|
| BlueZ (Linux default) | `bluer` advertising API or custom `zbus` interface | Running BlueZ `bluetoothd`, a BLE adapter, working system D-Bus, and authorization | Use `Advertisement.manufacturer_data[0x004C]`, intervals, and `Adapter::advertise`; retain adapter index selection. |
| WinRT (Windows default) | Microsoft `windows` crate bindings to `Windows.Devices.Bluetooth.Advertisement` | Windows BLE stack/adapter; API/capability status and publisher availability | Set manufacturer data, attach status event, start/stop. Keep `Waiting`, `Started`, and `Aborted` handling; `Start()` may wait or abort, and suspension stops advertising. |
| BleuIO (serial; default elsewhere) | `serialport` crate | External BleuIO dongle/firmware and serial permission/driver | Keep port discovery/selection, 115200 baud, 1-second read timeout, AT commands and response handling. This is hardware control, not host-native BLE. |
| HCI (explicit Linux/*BSD) | OS-specific command wrapper or Rust HCI API after target review | BLE HCI adapter; privileged raw HCI access or the source’s passwordless sudo commands | Preserve separately from BlueZ: HCI bypasses the daemon and has different privileges/adapter behavior. FreeBSD `hccontrol` behavior in the source is version-sensitive. |

**BlueZ.** BlueZ exposes advertising through the `org.bluez.LEAdvertisement1` D-Bus interface; ManufacturerData is a manufacturer-ID-to-bytes map and the API also accepts advertising intervals. The BlueZ API constructs the low-level advertisement from that structure. `bluer 0.17.4` directly models manufacturer data, `min_interval`, `max_interval`, and types; its advertisement API requires the `bluetoothd` feature. It still needs BlueZ and D-Bus, so only the payload and state logic are portable. [BlueZ Advertising API](https://bluez.readthedocs.io/en/latest/advertising-api/), [bluer Advertisement](https://docs.rs/bluer/latest/bluer/adv/struct.Advertisement.html).

**Strict BlueZ D-Bus parity.** The `bluer 0.17.4` convenience API generates its own advertisement object path and does not expose the source's `Release()` callback. The source path includes the CLI `index`, and `Release()` prints a removal message then exits 1; its asynchronous registration failure callback clears state without exiting, and stop awaits `UnregisterAdvertisement`. If those failure paths are in the compatibility bar, implement `org.bluez.LEAdvertisement1` directly with a service-side D-Bus API: `zbus::ObjectServer::at` registers an interface at a caller-chosen path, and the server supplies the standard `org.freedesktop.DBus.Properties` interface; `#[zbus::interface]` supports methods, properties and signals. A `zbus::proxy` trait can make typed calls to BlueZ ObjectManager, Adapter1 Properties and LEAdvertisingManager1. [zbus ObjectServer](https://docs.rs/zbus/latest/zbus/object_server/struct.ObjectServer.html), [zbus interface macro](https://docs.rs/zbus/latest/zbus/attr.interface.html), [zbus proxy macro](https://docs.rs/zbus/latest/zbus/attr.proxy.html).

**Windows WinRT.** Microsoft documents `BluetoothLEAdvertisementPublisher` as the publisher API and demonstrates manufacturer data through a company ID and byte buffer. It requires Bluetooth capability in packaged apps, reports `Waiting` when it cannot yet service the advertisement and `Aborted` on an immediate failure, and stops advertising when an app is suspended. UxPlay is not necessarily a packaged app, so verify unpackaged desktop deployment separately; use the Windows SDK API from `windows-rs` with narrowly enabled feature modules and preserve status transitions. [Microsoft BLE beacon guide](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/ble-beacon), [publisher Start behavior](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.advertisement.bluetoothleadvertisementpublisher.start), [windows-rs API crates](https://github.com/microsoft/windows-rs). Hardware and Windows policy remain runtime conditions, not Rust-level guarantees.

**Apple/macOS and BleuIO.** The original BleuIO module explicitly exists because the authors state that macOS user-level CoreBluetooth advertising cannot send manufacturer-specific data (`uxplay_beacon_module_BleuIO.py:1-11`). Apple’s `CBPeripheralManager.startAdvertising` only exposes local name and service UUID advertisement keys, which do not carry this Apple manufacturer-specific AirPlay payload. Retain the serial dongle backend for macOS; do not replace it with CoreBluetooth and claim equivalent payload behavior. [Apple CoreBluetooth startAdvertising](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/startadvertising%28_%3A%29), [Apple advertisement-data keys](https://developer.apple.com/documentation/corebluetooth/advertisement-data-retrieval-keys).

**BleuIO serial.** `serialport 4.10.1` provides blocking cross-platform port enumeration and I/O on POSIX and Windows, which fits the existing synchronous AT exchange. It does not implement BLE or the dongle firmware protocol. Preserve the source’s exact `AT+ADVDATA`, `AT+ADVSTART`, and `AT+ADVSTOP` sequences, selected serial device and interval validation. The docs.rs project currently says it is looking for maintainers, especially for Windows; isolate it behind one adapter and pin/compile-test the intended platforms. [serialport API](https://docs.rs/serialport/latest/serialport/), [platform and maintenance notes](https://docs.rs/crate/serialport/latest).

**Direct HCI.** This is the least portable backend. The supplied source requires passwordless `sudo -n` for `hcitool`/`hciconfig` on Linux and `hccontrol` on FreeBSD, and documents a FreeBSD-before-15.1 compatibility patch requirement (`uxplay_beacon_module_HCI.py:1-64`). Treat it as an opt-in backend with an explicit privilege preflight, bounded command execution, stderr/exit-code mapping, and adapter selection. It cannot be reduced to safe Rust logic alone: either call the host utilities (retaining their version dependency) or implement raw HCI against each OS’s Bluetooth stack and validate permissions/commands per release.

## Port architecture

1. Keep a pure Rust `AirplayBeaconPayload` builder for Apple company ID, payload bytes, port byte order and AD-length accounting.
2. Define `BleBackend::{BlueZ, WinRt, BleuIo, Hci}`; retain auto-default selection by target OS and explicit CLI/config choice. Do not remove less-common HCI/BleuIO paths merely because native Windows/Linux APIs exist.
3. Let each backend own startup, async status/registration callbacks, stop/unregister, adapter/device discovery, and platform error translation. Use `cfg(target_os)` plus Cargo feature flags so Windows-only WinRT APIs and Linux-only BlueZ APIs do not leak into portable modules.
4. Keep CLI options and emitted status/error/exit behavior at the shared boundary. Acceptance should compare emitted service records, parsed binary plist fixtures, BLE payload bytes, CLI stdout/stderr/exit codes, and start/stop cleanup against the source modes.
5. Keep backend integration separate from the protocol layer: embedded mDNS/plist/payload construction can be Rust-only; native DNS-SD delegates to Bonjour/WinDNS/Avahi; BlueZ and WinRT delegate to OS Bluetooth services; BleuIO needs external serial hardware; HCI needs OS-specific low-level access and privileges.
