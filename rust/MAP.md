### Critical-path priorities

Reconcile this order with the current code at every cycle; skip verified work and change order only when dependency evidence makes another batch more productive.

1. **Protocol-critical correctness:** complete legacy FairPlay/PlayFair, cryptography and pairing; missing AirPlay/RTSP/RAOP behavior; encrypted audio/video session handling and media decryption; packet/callback delivery; session setup, reconnect, timeout, reset and teardown; and remove runtime dependencies on the original executable from the Rust-owned server path. 2. **Functional runtime integration:** complete and verify service discovery, pairing/authentication, audio playback, mirroring/video decode, A/V sync, RTP/NTP, HLS and reverse FCUP lifecycle, renderer switch/cancel/recovery/shutdown, MP4 finalization, dump output, CLI-to-runtime options, registration persistence, and BLE handoff/beacon lifecycle. Reuse fixtures and tools; compare identical deterministic inputs against the unchanged C reference when possible. Normalize only genuine nondeterminism such as timestamps, ephemeral ports and cryptographic randomness. Simulations do not prove Apple-device interoperability.
4. **Compatibility and standalone release:** complete CLI/config/environment and platform-specific behavior, native dependencies/cross-target builds and all remaining source-unit gates; use documented equivalent C-oracle evidence where generic `rust-anything` cannot model pointer/state APIs. The Rust server is normal startup; Windows arguments now pass through C's active ANSI code page and CLI behavior. Remove remaining unrepresentable-argument forwarding and rollback paths only after full acceptance. The final standalone build must neither depend on nor silently invoke the reference executable; retain an explicit development comparison mode only if useful.
5. **Performance, stability and packaging:** after correctness, compare CPU, memory, startup, stream latency/throughput and A/V sync; investigate measured regressions; review allocations, threading, ownership, cleanup and long-run stability; prepare reproducible release builds and packaging. Do not prematurely optimize unverified functionality.

### Verification and engineering rules

Reuse existing Cargo caches, build artifacts, fixtures, oracles and harnesses; do not clean-build, reinstall dependencies, or rerun commands with unchanged known-failing prerequisites. Use focused checks while developing and batch formatting, Clippy, full tests, broad replay and release builds at subsystem acceptance boundaries. Never skip a required original acceptance gate. Preserve source semantics, bytes, serialization, arithmetic, timing, errors, exit behavior and resource lifecycle. Keep Rust safe and idiomatic; confine justified `unsafe` to FFI/platform boundaries and avoid unnecessary dependencies or unrelated refactors. Do not add placeholders, fabricate responses, silently swallow errors, add silent C fallback to mask missing Rust behavior, weaken tests/fixtures/assertions, or mark work complete without evidence. When source behavior is unusual, distinguish compatibility requirements from safe improvements and never change observable behavior silently.
